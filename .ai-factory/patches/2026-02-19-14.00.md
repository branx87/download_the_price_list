# Массовые UPDATE через временные таблицы MSSQL вместо построчных

**Date:** 2026-02-19 14:00
**Files:** adapters/database/sql_repository.py
**Severity:** high

## Problem

Три метода делали N построчных UPDATE вместо одного массового:

- `bulk_set_article_pc`: 44365 UPDATE за ~83с (ERP привязка ArticlePC)
- `update_items`: N UPDATE батчами по 500 (обновление прайсов из Excel)
- `add_erp_items` UPDATE часть: N UPDATE батчами по 1000 (ArticlePC для уже существующих)

VBA делает то же самое быстрее, потому что использует временную таблицу + JOIN UPDATE — одна операция на стороне SQL Server.

## Root Cause

Паттерн `connection.execute(query, list_of_dicts)` в SQLAlchemy с WHERE по ключам — это **N отдельных UPDATE запросов** (executemany = цикл). Каждый запрос:
- Отдельный network round-trip
- Отдельный поиск по индексу
- Отдельная запись в transaction log

Для 44365 записей = 44365 round-trips. VBA использует временную таблицу и один JOIN UPDATE = один round-trip.

## Solution

Для MSSQL добавлен путь через временную таблицу в трёх методах:

```python
# Создаём временную таблицу (connection-scoped, видна только нашей сессии)
connection.execute(text("CREATE TABLE #tmp_xxx (...)"))

# Массовая вставка батчами по 1000 (INSERT быстрее UPDATE, нет конкурентных блокировок)
for i in range(0, len(data), 1000):
    connection.execute(text("INSERT INTO #tmp_xxx ... VALUES (...)"), data[i:i+1000])

# ОДИН JOIN UPDATE — весь объём за одну операцию на SQL Server
result = connection.execute(text("""
    UPDATE tp
    SET tp.Field = t.Field, ...
    FROM Total_Price tp
    INNER JOIN #tmp_xxx t ON tp.Vendor = t.Vendor AND tp.Part_Num = t.Part_Num
"""))

connection.execute(text("DROP TABLE #tmp_xxx"))
session.commit()
```

Ключевые моменты:
- `#tmp_xxx` (одинарный `#`) — локальная временная таблица, видна только текущему соединению
- Нет промежуточных `commit()` — один commit в конце (нет проблемы "Connection is closed")
- `session.connection()` вызывается ОДИН РАЗ до цикла вставки (нет commit между вызовами)
- Для SQLite сохранён старый путь (executemany), т.к. SQLite — локальная БД без network overhead

Изменены методы:
- `bulk_set_article_pc` — temp table `#tmp_apc`
- `update_items` — temp table `#tmp_price_upd`
- `add_erp_items` UPDATE часть — temp table `#tmp_erp_upd`

## Prevention

**Правило для массовых UPDATE в MSSQL:**

Если нужно обновить > 100 записей с разными значениями для каждой — используй временную таблицу:

1. `CREATE TABLE #tmp (ключи, значения)`
2. `INSERT INTO #tmp ... executemany (батчами по 1000)`
3. `UPDATE target INNER JOIN #tmp ... SET target.val = tmp.val`
4. `DROP TABLE #tmp`
5. `COMMIT`

НЕ используй N отдельных `UPDATE ... WHERE key = ?` для большого числа записей.

**Ожидаемое ускорение:**
- `bulk_set_article_pc`: 83с → 2-3с (в 30x раз)
- `update_items`: пропорционально количеству записей
- `add_erp_items` UPDATE: аналогично
