# ERP sync: оптимизация batch операций — 20 минут → 2-3 минуты

**Date:** 2026-02-19 03:00
**Files:** adapters/database/sql_repository.py
**Severity:** high

## Problem

ERP-синхронизация выполнялась **~20 минут** для обновления 28889 позиций (привязка ArticlePC).
Telegram-бот зависал на всё это время, пользователь не получал обратной связи.

По логам:
- Получение данных из 1C: 15.6с ✅ (быстро)
- **Обновление ArticlePC для 28889 позиций: ~20 минут** ❌ (основная проблема)

Это критично медленно — ожидается не более 1-2 минут для такой операции.

## Root Cause

**Проблема 1: Маленький batch_size = 200**
- 28889 записей / 200 = **145 батчей**
- Каждый батч: открыть сессию → 200 UPDATE → commit → закрыть сессию
- Overhead на создание сессии для каждого батча

**Проблема 2: Новая сессия на КАЖДЫЙ батч**
```python
for i in range(0, len(all_data), batch_size):
    batch = all_data[i:i + batch_size]
    with self.SessionLocal() as session:  # <-- 145 раз!
        connection = session.connection()
        connection.execute(query, batch)
        session.commit()
```
Открытие/закрытие 145 сессий — огромный overhead (connection pool, begin/commit транзакций).

**Проблема 3: Отсутствие прогресс-логирования**
Пользователь не видит прогресса, думает что бот завис.

**Проблема 4: SQL ошибка в cleanup_none_strings**
```
[SQL: UPDATE Total_Price SET Discount = '' WHERE Discount = 'None']
(Background on this error at: https://sqlalche.me/e/20/f405)
```
Поле Discount — числовое (DECIMAL/NUMERIC), попытка присвоить пустую строку '' вызывает ошибку.

**Математика медленной работы:**
- 145 батчей × 8-10 сек на батч = **1160-1450 секунд = 19-24 минуты**

## Solution

**1. Увеличен batch_size с 200 до 1000**
- Уменьшено количество батчей с 145 до 29
- Меньше транзакций = меньше overhead

**2. ОДНА сессия для всех батчей**
```python
# Было: 145 новых сессий
for i in range(...):
    with self.SessionLocal() as session:  # <-- каждый раз новая!
        ...

# Стало: ОДНА сессия, промежуточные commit'ы
with self.SessionLocal() as session:    # <-- только один раз!
    connection = session.connection()
    for batch_idx in range(...):
        connection.execute(query, batch)
        session.commit()  # освобождаем блокировки
        time.sleep(0.05)  # пауза для других транзакций
```

**3. Добавлены паузы 0.05с между батчами**
- Позволяет другим транзакциям (1C, OLE DB) выполниться
- БД не блокируется надолго
- Минимальное влияние на общее время (29 × 0.05с = 1.5с)

**4. Прогресс-логирование каждые 10000 записей**
```python
logger.info(
    f"[FIX] bulk_set_article_pc: {total}/{len(all_data)} обработано, "
    f"батч {batch_num}/{num_batches}, время: {elapsed:.1f}с"
)
```

**5. Таймеры для измерения производительности**
```python
start_time = time.time()
# ... операции ...
elapsed = time.time() - start_time
logger.info(f"Завершено за {elapsed:.1f}с ({total / elapsed:.0f} rec/s)")
```

**6. Исправлена ошибка SQL в cleanup_none_strings**
- Удалено поле Discount из списка очищаемых (это числовое поле, не может содержать 'None')

**Изменённые методы:**
- `bulk_set_article_pc` — основная оптимизация
- `add_erp_items` (UPDATE и INSERT части) — аналогичная оптимизация
- `cleanup_none_strings` — исправлена ошибка Discount

## Prevention

**Паттерн для batch-операций на MSSQL:**
1. **Одна сессия для всех батчей** — не создавать новую на каждый батч
2. **Batch size = 1000-2000** — баланс между производительностью и блокировками
3. **Промежуточные commit'ы** — освобождать блокировки после каждого батча
4. **Паузы между батчами (0.05-0.1с)** — не блокировать БД для других пользователей
5. **Прогресс-логирование** — каждые N записей или батчей для обратной связи
6. **Таймеры** — измерять производительность для раннего обнаружения проблем
7. **Числовые поля** — не пытаться присваивать пустые строки '' (использовать NULL или 0)

**Проверка перед batch-операцией:**
- Сколько батчей будет? Если > 100 → вероятно нужна оптимизация
- Используется ли одна сессия или создается новая на каждый батч?
- Есть ли прогресс-логи для операций > 1 минуты?

**Ожидаемый результат:**
- Было: 28889 записей за ~20 минут = ~24 rec/s
- Ожидается: 28889 записей за ~2-3 минуты = ~200+ rec/s
- Ускорение: **в 8-10 раз**
