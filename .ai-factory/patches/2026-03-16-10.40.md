# RuntimeError: ExtBot is not properly initialized при запуске бота

**Date:** 2026-03-16 10:40
**Files:** bot/main.py
**Severity:** critical

## Problem

Бот не запускался. Падал с ошибкой:
```
RuntimeError: ExtBot is not properly initialized. Call `ExtBot.initialize` before accessing this property.
```
Также в логах был `httpcore.ConnectTimeout` при попытке `get_updates` во время shutdown.

## Root Cause

Цепочка причин:

1. **Медленная сеть** — `get_me()` занимал > 30с из-за нестабильного соединения с api.telegram.org.

2. **Баг в python-telegram-bot 22.x** — в `Bot.initialize()` флаг `_initialized=True` устанавливается ДО вызова `get_me()`. Если `get_me()` падает с `TimedOut`, при повторной попытке `initialize()` видит `_initialized=True` и сразу возвращает управление — `get_me()` не вызывается, `_bot_user` остаётся `None`. Затем `Application.start()` обращается к `self.bot.id` → `_bot_user is None` → `RuntimeError`.

3. **`proxy_url()` удалён из ptb 22.x** — метод в `ApplicationBuilder` теперь называется `proxy()`, старый вызов `builder.proxy_url()` молча не делал ничего.

4. **`get_updates_request` без явных таймаутов** — по умолчанию `connect_timeout=5.0`, что ломается при медленной сети.

## Solution

1. **Monkey-patch `Bot.initialize`** — перед вызовом оригинального метода проверяем: если `_initialized=True` но `_bot_user is None`, сбрасываем флаг. Это позволяет корректно повторить `get_me()`.

2. **Явно задаём `get_updates_request`** с увеличенными таймаутами (60с) — оба request-объекта нужно конфигурировать вместе, иначе один остаётся с дефолтными 5с таймаутами.

3. **Исправлен `proxy_url()` → `proxy=` параметр** в `HTTPXRequest`, прокси применяется к обоим request-объектам.

4. **`bootstrap_retries=-1`** — бесконечные ретраи при проблемах сети при запуске.

5. **`post_init` callback** — статус "бот запущен" теперь выводится только после успешного подключения.

## Prevention

- При обновлении python-telegram-bot проверять changelog на изменения в API Builder и инициализации.
- Всегда настраивать оба request-объекта (`request` и `get_updates_request`) с одинаковыми таймаутами.
- Тестировать поведение при медленной сети (ConnectTimeout) отдельно от нормального запуска.
