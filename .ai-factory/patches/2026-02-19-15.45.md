# ERP sync: дубли из-за игнорирования синонимов при поиске Vendor+Part_Num

**Date:** 2026-02-19 15:45
**Files:** domain/services/erp_sync_service.py, adapters/database/sql_repository.py
**Severity:** high

## Problem

ERP-синхронизация создавала дубли для позиций чьи вендора записаны в БД через синоним:
- Таблица VendorSynonyms содержит: `1SE -> SE`, `A-SE -> SE`
- В Total_Price есть запись с `Vendor='1SE'`, `Part_Num='SOME_ART'`
- ERP присылает позицию с `manufacturer='SE'` → после нормализации `'SE'`
- Код проверяет `('SE', 'SOME_ART') in existing_pairs` → False (в БД `'1SE'`, не `'SE'`)
- Результат: создаётся дубль вместо привязки ArticlePC

Дополнительно: ошибка при старте:
```
ERROR - Ошибка очистки 'None' в колонке Labor:
Error converting data type varchar to float.
[SQL: UPDATE Total_Price SET Labor = '' WHERE Labor = 'None']
```
Колонка `Labor` имеет тип FLOAT в MSSQL, нельзя SET = '' (пустая строка).

## Root Cause

**Проблема 1: Поиск по Vendor без учёта синонимов**

`existing_pairs` загружался через `get_all_vendor_part_num_pairs()`, который возвращает
нормализованные пары `(Vendor, Part_Num)` из реальных записей БД. Но синонимы в
VendorSynonyms говорят что `1SE IS-A SE` — то есть `1SE` и `SE` это один вендор.

При поиске `('SE', article) in existing_pairs` совпадение с `('1SE', article)` не находилось,
и код шёл в INSERT вместо UPDATE ArticlePC.

Также: при UPDATE использовался `manufacturer` (из ERP, = `'SE'`), а не реальный вендор из БД.
Даже если бы совпадение нашлось, UPDATE WHERE Vendor='SE' не нашёл бы запись с Vendor='1SE'.

**Проблема 2: Labor — FLOAT колонка, не varchar**

`cleanup_none_strings()` обрабатывает `Labor` как строковое поле, пытаясь выполнить:
`UPDATE Total_Price SET Labor = '' WHERE Labor = 'None'`
Это падает с "Error converting data type varchar to float" потому что `Labor` — FLOAT в MSSQL,
и '' не конвертируется в FLOAT.

## Solution

**1. Synonym-aware lookup в `erp_sync_service.py`:**

Вместо простой проверки в `existing_pairs` (set) строим `pair_to_db_vendor` (dict):

```python
# {(vendor_или_canonical, part_num) -> actual_db_vendor}
pair_to_db_vendor = {}
for vendor, part_num in existing_pairs:
    pair_to_db_vendor[(vendor, part_num)] = vendor
    if vendor in synonyms_map:
        canonical = synonyms_map[vendor]
        if (canonical, part_num) not in pair_to_db_vendor:
            pair_to_db_vendor[(canonical, part_num)] = vendor  # -> реальный вендор в БД
```

Теперь:
- `('SE', 'SOME_ART')` находится в pair_to_db_vendor со значением `'1SE'`
- `db_vendor = pair_to_db_vendor[('SE', 'SOME_ART')]` = `'1SE'`
- UPDATE использует `vendor='1SE'` → правильно обновляет запись

Также логируется когда найдено через синоним:
```
[ERP] Найдено через синоним: 'SE' -> '1SE' | SOME_ART
```

**2. Удалён `Labor` из `cleanup_none_strings()`:**

```python
# Было:
columns = ['Storage', 'Currency', 'URL', 'Labor', 'LaborCategory', ...]

# Стало:
# Discount, Labor исключены — числовые поля FLOAT, не могут содержать 'None'
columns = ['Storage', 'Currency', 'URL', 'LaborCategory', ...]
```

## Prevention

**Правило lookup с синонимами:**

Когда ищем данные по вендору — всегда проверяем: может в БД вендор хранится под другим именем,
которое через синонимы относится к тому же canonical имени.

Чеклист для операций сравнения/поиска по вендорам:
1. Загрузить synonyms_map (`{vendor -> canonical}`)
2. Построить reverse lookup: для каждой DB-записи добавить ключ по canonical имени
3. При нахождении через синоним — использовать РЕАЛЬНЫЙ вендор из БД в UPDATE

**Правило для числовых колонок в cleanup:**

Не включать FLOAT/INT/DECIMAL колонки в string-cleanup операции.
Числовые колонки не могут содержать строку 'None' — в MSSQL это бы вызвало ошибку конверсии.
Список безопасных для очистки строк: только явно VARCHAR/NVARCHAR поля.
