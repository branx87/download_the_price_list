# ERP sync: одни и те же 3 позиции привязываются при каждом запуске

**Date:** 2026-02-19 18:00
**Files:** adapters/database/sql_repository.py
**Severity:** medium

## Problem

При каждом вызове `/erp` одни и те же 3 позиции отображались как "Привязано ArticlePC: 3",
хотя должны были привязаться единожды и стать "пропущенными" при следующих запусках:

```
📥 Получено из 1C: 44382
➕ Добавлено новых: 0
🔗 Привязано ArticlePC: 3    ← одно и то же каждый раз
⏭ Пропущено (уже есть): 44379
```

## Root Cause

Несоответствие нормализации Part_Num между кодом и БД.

`normalize_article()` делает `re.sub(r'\s+', '', article)` — убирает ВСЕ внутренние пробелы.
`cleanup_whitespace()` делал только `LTRIM/RTRIM` — убирал только LEADING/TRAILING пробелы.

Цепочка:
1. В БД хранится `Part_Num = 'ABC 123'` (с внутренним пробелом)
2. `get_all_vendor_part_num_pairs()` нормализует через `normalize_article()` → `('VENDOR', 'ABC123')`
3. ERP артикул нормализуется → `'ABC123'` → совпадение найдено в lookup → позиция идёт в `to_update_article_pc`
4. `to_update_article_pc` содержит `part_num = 'ABC123'` (нормализованный)
5. `bulk_set_article_pc` делает `INSERT INTO #tmp_apc VALUES ('VENDOR', 'ABC123', 'CODE', ...)`
6. JOIN: `ON tp.Part_Num = 'ABC123'` vs DB `Part_Num = 'ABC 123'` → **0 строк найдено**
7. ArticlePC в БД НЕ устанавливается
8. Следующий запуск: те же 3 позиции снова попадают в "привязку"

## Solution

В `cleanup_whitespace()` добавлен шаг удаления внутренних пробелов из Part_Num:

```sql
UPDATE Total_Price
SET Part_Num = REPLACE(Part_Num, ' ', '')
WHERE Part_Num IS NOT NULL AND Part_Num != ''
  AND Part_Num != REPLACE(Part_Num, ' ', '')
```

Это идемпотентная операция, выполняется при каждом старте бота.
Работает для MSSQL и SQLite без ветвления (REPLACE доступен в обоих).

Дополнительно добавлен warning-лог в `bulk_set_article_pc` если обновлено 0 строк при непустом входе —
для раннего обнаружения подобных несоответствий в будущем.

## Prevention

**Правило консистентности нормализации:**

Если код нормализует значение перед сравнением/поиском, то:
1. Значения в БД тоже должны быть нормализованы (cleanup при старте)
2. ИЛИ SQL запрос должен применять ту же трансформацию в WHERE

Чеклист при добавлении новой нормализации в DataNormalizer:
- [ ] Добавить соответствующую SQL-нормализацию в `cleanup_whitespace()`
- [ ] Убедиться что UPDATE-запросы используют нормализованные значения корректно

Симптом несоответствия: `bulk_set_article_pc: 0 строк обновлено при N входных записях`
(теперь это логируется как WARNING).
